# PRD 21 — Design, Capability and Dependency Research Register

## Research discipline
Use current official product docs to discover capabilities and maintained library/model docs for technical claims. Check exact versions, weight licenses, APIs, language coverage, current security advisories and redistribution rights before selection. Record source URL, retrieval date, exact version/checkpoint, notes and how validated. Online search results alone are not implementation evidence.

The parity PRD is an evolving inventory; current docs and a feature-by-feature audit decide exact functionality and exclusions. Research workflows, not just marketing bullet points. Distinguish offline desktop functions from hosted storage, collaboration, live review, cloud signature and cloud AI.

## Model/library evidence card
For every dependency/model record version/commit/checkpoint hash, source/maintenance, licenses for code/weights/tokenizer/data/fonts/runtime, redistribution/commercial/modification/attribution requirements, security status, platform compatibility, install size, RAM/VRAM, offline behavior, quality metrics, output examples, known weaknesses and chosen alternative. A code license may not cover weights or training data. Reject unclear/noncommercial artifacts by default unless owner explicitly approves a limitation.

Candidates discussed for evaluation—not automatic choices—include PaddleOCR/PaddleOCR-VL; Docling as a pipeline/framework; Table Transformer; MADLAD-400-3B-MT; OPUS-MT direction-specific models; mature PDF rendering/Office converters; and suitable speech/vision runtimes. Verify exact current versions/checkpoint licenses and benchmarks.

## Visual design research
Record screenshot/reference URL, date, feature, observed interaction, design inspiration and what PageWeave implements differently. Never distribute reference images or embed their assets into the software unless rights allow it. No UI branding that implies Adobe affiliation.
